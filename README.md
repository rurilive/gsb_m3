# idemkey

支付链路的幂等键存储：按幂等键记住已处理请求的结果，同一个键再提交时
回放上次的结果，避免重复扣款。纯标准库，无外部依赖。

## 模块说明

`idemkey/store.py` 提供 `IdempotencyStore(ttl=None, clock=time.monotonic,
path=None, max_result_size=None)`：

- `begin(key)`：提交前问这个键要不要干活。返回 `True` 表示该由本次请求
  处理；返回 `False` 表示这个键已经处理过，调用方改用 `get(key)` 回放结果
- `finish(key, result)`：把处理结果记到键上，这个键之后就算已处理
- `fail(key)`：处理中途失败时调用，释放 `begin()` 占上的占位，同一键
  随后可以重新 `begin()`；已经 `finish` 的结果不受影响
- `renew(key)`：以当前时刻续期。处理中的长流程可以中途续命不必重跑；
  已经完成的记录调用后，回放窗口从现在起再顺延一个 `ttl`
- `get(key)`：取这个键已记下的结果，没有就返回 `None`
- `ttl`：记录存活秒数，`None` 表示永不过期
- `clock`：时间读取统一走它，便于测试注入
- `path`：记录落盘的文件路径，`None` 表示只放内存
- `max_result_size`：结果 JSON 序列化后的 UTF-8 字节上限，超出则不存原
  结果，只存一份 `TruncatedResult` 截断标记；`None` 表示不限制

键的规范化只去掉首尾空白，**保留原始大小写**（大小写不同即不同的键）。

截断标记 `idemkey.TruncatedResult` 带有 `original_size`、`limit` 和
`preview`（原结果序列化文本的开头片段）字段，`get()` 取回后用
`isinstance(result, TruncatedResult)` 即可认出这份结果被截断过；标记同样
会随磁盘持久化、跨重启保留。

记录字段：`result` 保存结果，`created_at` 是键被占上的时刻，`finished_at`
是收尾时刻。内部一把锁保护，磁盘读写也在锁内完成。

## Known Issues
以下四类对账怪象均已修复（现象、根因、修法逐条记录在此），对应防回归
测试见 `tests/test_regression.py`。

1. **只差大小写的两笔单号被当成同一笔，后一笔拿回前一笔的回执。**
   - 根因：键规范化在去空白之外还做了 `lower()`，`Order-7001` 与
     `order-7001` 塌缩成同一个键，`begin()` 直接判重、`get()` 回放的是
     另一笔单子的回执；运营误判未扣款而补发，用户被多扣。
   - 修法：规范化只保留 `strip()`，去掉 `lower()`，键大小写敏感。
2. **服务半夜重启后，处理过的单子像从没记过、一个都取不回，键却还在，
   重发全被判重复卡住。**
   - 根因：`begin()` 会 `_save()`，但 `finish()` 从不落盘。磁盘上只有
     开工时写入的占位记录（`result=null`、`finished_at=null`），重启后
     记录被原样读回：`get()` 拿到 `None`，`begin()` 又因键存在而判重，
     单子既取不到回执也无法重做。
   - 修法：`finish()`（以及 `fail()`、`renew()`）都在锁内 `_save()`；
     落盘改为同目录临时文件 + `os.replace` 原子替换，避免写一半崩溃留下
     半截 JSON。此外 `_load()` 会丢弃 `finished_at` 为空的开工占位——
     这说明上次进程崩在 `finish()` 之前，重启即视为没处理过、允许重做，
     避免崩溃残留把键永久卡死。
3. **处理到一半下游超时失败，那个键从此起不来工，重发只回空结果。**
   - 根因：`begin()` 先占键占位，处理过程抛异常时没有任何释放路径；
     占位永久留在表里，后续 `begin()` 恒为 `False`、`get()` 恒为
     `None`，单子永远发不出去。
   - 修法：新增 `fail(key)`，处理失败时调用，删除未收尾的占位并落盘，
     同一键立刻可以重新提交；已完成的结果不会被 `fail()` 抹掉。
4. **耗时长的单子刚收工去取就说不认识，离有效期还早。**
   - 根因：过期清理由 `now - created_at >= ttl` 判定，TTL 名义上“从完成
     时刻起算”，实现却按开工时刻算。单子处理时间一旦超过 TTL，记录在
     `finish()` 之前就已过期，收工瞬间即被清掉。
   - 修法：过期起算点按记录状态区分：已完成记录用 `finished_at`，未
     收尾的占位才用 `created_at`。长单收工后重新获得完整的一个 TTL；
     处理中的占位若真的超过 TTL（例如 worker 死掉没人 `fail()`），依旧
     会被清掉允许接管，不会永久占坑。

新增能力：

- **按完成时刻续期 / 长流程中途延长**：新增 `renew(key)`，处理中的占位
  以当前时刻重置开工时刻，长流程可在中途续期而不必整单重跑；已完成记录
  则以当前时刻重置完成时刻，把回放窗口顺延一个 TTL。
- **超大结果落截断标记**：新增 `max_result_size` 参数。`finish()` 时若
  结果的 JSON 序列化字节数超过上限，不把大对象放进缓存/磁盘，而是存
  `TruncatedResult` 标记（含原始体积、上限与开头预览），`get()` 取回后
  可凭类型识别“这份结果被截断过”，标记本身远小于上限，不会撑爆缓存，
  且同样持久化、跨重启保留。
