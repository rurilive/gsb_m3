# ringbuf

多生产者/多消费者定长环形缓冲，网关进程内嵌使用，纯标准库（threading.Lock）。

## 语义

- `put(item)`：写入一个元素，永不阻塞；缓冲满时覆盖最老元素，count 不会超过容量
- `get()`：取出最老元素；缓冲为空时抛 `ringbuf.Empty`；每条消息只会被一个消费者取到
- `count()`：当前元素个数，取值范围 [0, capacity]
- `snapshot()`：按逻辑顺序（写入顺序）导出当前内容的副本，不影响缓冲状态
- 所有操作线程安全，可在多线程读写场景下直接使用

## 运行

```bash
python3 demo.py
```

## Known Issues

以下缺陷已修复（防回归测试见 `tests/`，`python3 -m unittest discover -s tests` 运行）：

- **count 只涨不跌、可超过容量（已修复）**：`put` 在缓冲满淘汰最老元素时只推进了读游标，漏了同步扣减 count，每覆盖一次 count 虚增 1；同时 `get` 的 count 扣减在锁外执行，并发下丢失更新。修复：淘汰时同步扣减，且 get 全程持锁。
- **同一条消息被两个消费者取到（已修复）**：`get` 只在锁内读取元素，游标推进和 count 扣减在锁外，两个消费者可读到同一槽位的同一条消息。修复：读取、游标推进、计数扣减合并在同一把锁内完成。
- **缓冲未满却丢消息（已修复）**：缓冲区物理槽位为 capacity+1 个，写游标按 `> capacity` 回绕，而读游标错误地按 `>= capacity` 提前一格回绕，永远跳过最后一个槽位，写入该槽位的消息永远无法被消费。修复：读写游标回绕条件保持一致。
- **snapshot 顺序与写入顺序不符（已修复）**：旧实现直接截取物理数组头部 `list(buf)[:count]`，未从读游标按逻辑顺序展开。修复：从 head 起按 count 个元素回绕展开，导出顺序即写入顺序。
