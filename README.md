# delayq

任务编排平台的延时队列，heapq 实现，时钟注入，纯标准库，无外部依赖。

## 模块说明

`delayq/queue.py` 提供延时队列 `DelayedQueue(clock=None)`：

- `add(task, delay, key=None)`：任务在 delay 秒后到期；key 相同的重复
  提交以最后一次为准，旧条目作废，不会被再次执行
- `pop_ready()`：只弹出已到期（due <= 当前时刻）的任务；同一时刻到期
  的任务按提交顺序出队；没有到期任务时返回 None
- `peek()`：距最近到期任务的等待秒数，消费端按它睡眠后再轮询；队列
  为空返回 None
- `len(q)`：当前排队条目数

`delayq/clock.py` 提供时钟抽象：`SystemClock` 为进程默认时钟，
`FakeClock` 支持 `advance()` / `jump_to()` 手动推进，供测试注入。

## 运行

```bash
python3 demo.py
```

## Known Issues

以下为上线初期反馈的四个问题，均已修复（对应回归测试见 `tests/`）：

1. **未到期任务被提前执行**
   根因：旧版 `pop_ready()` 直接 `heappop` 返回堆顶，完全没有拿当前
   时钟与 `due` 比较，只要队列非空就会弹出任务。现在弹出前先判断
   `due <= clock.monotonic()`，未到期的堆顶留在堆中并返回 `None`。

2. **同一时刻到期的任务执行顺序飘忽**
   根因：堆元素是 `(due, delay, entry)`，同 `due` 时退化为比较
   `delay`（同刻任务 delay 通常也相同），再退化为 `_Entry` 对象
   的对象 ID 比较；而旧 `_Entry.__lt__` 只比 `due`，相等时结果
   取决于解释器内存布局，每次运行顺序都不同，隔天表现自然不一致。
   现在堆元素为 `(due, seq, entry)`，`seq` 是全局单调递增的提交
   序号，保证同刻任务严格按提交顺序（FIFO）出队。

3. **同一 key 重复提交后任务执行两次**
   根因：旧版 `add()` 收到带 `key` 的任务时只做普通入堆，`key`
   参数被完全忽略，没有任何去重或作废机制，旧条目到期后照样被
   弹出。现在维护 `key -> 当前条目` 映射：同 key 再次提交时旧条目
   标记为失效（惰性删除），`pop_ready()`/`peek()` 跳过失效条目，
   只有最后一次提交会执行；`len(q)` 也不再计入失效条目。

4. **消费端 CPU 打满空转 / 一口睡过头错过整批任务**
   根因：旧版 `peek()` 直接返回堆顶的绝对到期时间戳
   `entry.due`（例如 102.0），而文档约定的是"距最近到期任务的
   等待秒数"。消费端把绝对时间戳当成睡眠时长：任务临近到期时
   返回一个很小甚至为 0 的值，于是醒后立刻轮询、忙等空转 CPU；
   时钟基准较大时（如单调时钟零点是启动时刻，读数为上千秒）则
   一口气睡过成百上千秒，错过整批任务。此外旧版 `peek()` 不跳过
   失效的旧 key 条目，也会基于已作废条目报告错误的等待时长。
   现在 `peek()` 先惰性清理失效条目，再返回
   `max(0.0, due - clock.monotonic())`，即真正的剩余等待秒数。
