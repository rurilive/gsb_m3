# idemkey

支付链路的幂等键存储：按幂等键记住已处理请求的结果，同一个键再提交时
回放上次的结果，避免重复扣款。纯标准库，无外部依赖。

## 模块说明

`idemkey/store.py` 提供 `IdempotencyStore(ttl=None, clock=time.monotonic,
path=None)`：

- `begin(key)`：提交前问这个键要不要干活。返回 `True` 表示该由本次请求
  处理；返回 `False` 表示这个键已经处理过，调用方改用 `get(key)` 回放结果
- `finish(key, result)`：把处理结果记到键上，这个键之后就算已处理
- `get(key)`：取这个键已记下的结果，没有就返回 `None`
- `ttl`：记录存活秒数，`None` 表示永不过期
- `clock`：时间读取统一走它，便于测试注入
- `path`：记录落盘的文件路径，`None` 表示只放内存

记录字段：`result` 保存结果，`created_at` 是键被占上的时刻，`finished_at`
是收尾时刻。内部一把锁保护，磁盘读写也在锁内完成。

## 运行

```bash
python3 demo.py                          # 现象演示
python3 -m unittest discover -s tests -v # 行为基线测试
```

## Known Issues

以下四类线上事故均已修复，根因与修法记录在此，`tests/test_regressions.py`
里有对应的防回归测试。

### 1. 只差大小写的单号被并成一笔（已修复）

- 现象：两个单号只差大小写（如 `Order-7001` 与 `order-7001`）被当成同一
  笔，后一笔 `begin` 直接返回 `False`，`get` 拿回前一笔的回执，运营误判
  未扣款后补单，用户被重复扣款。
- 根因：`_normalize` 在去掉首尾空白之外还做了 `.lower()`，把大小写不同
  的键折叠成同一个。
- 修法：键的规范化只保留去首尾空白，大小写敏感，不同的单号各自占键。

### 2. 服务重启后键还在、结果没了（已修复）

- 现象：进程重启后，之前处理过的键仍然存在，`begin` 返回 `False` 把重发
  判成重复，但 `get` 只能取回 `None`，单子卡死。
- 根因：落盘 `_save()` 只在 `begin` 占键时调用，`finish` 写回结果后没有
  再落盘，磁盘上永远只有 `result=None` 的半成品记录。
- 修法：`finish` 写回结果后立即落盘；`_purge` 清掉过期记录后同步落盘，
  保证磁盘与内存一致。

### 3. 处理中途失败后键被卡死（已修复）

- 现象：一单处理到一半下游超时失败，之后该键 `begin` 永远返回 `False`，
  `get` 永远返回 `None`，重发只回一份空结果，再也起不了工。
- 根因：`begin` 占键后，只要记录存在就一律返回 `False`，不区分"已收尾"
  和"中途失败留下的残键"；失败的请求永远不会调 `finish`，键就此卡死。
- 修法：`begin` 只对已收尾（`finished_at` 非空）的记录返回 `False`；没收
  尾的残键视为上次处理失败，允许重新占键开工。注意：这意味着同一键的在
  飞并发请求不再由 `begin` 拦截，调用方需自行串行化同一键的在飞处理；
  防重保证落在"已收尾的记录回放结果"上。

### 4. 耗时单收工即过期（已修复）

- 现象：一笔耗时较长的单子刚 `finish`，`get` 就取不到结果，明明离有效期
  还早。
- 根因：`_purge` 用 `created_at`（占键/开工时刻）起算 TTL，与文档承诺的
  "从请求完成时刻起算"不符；处理耗时超过 TTL 的单子收工即被清掉。
- 修法：有效期起算点改为 `finished_at`（已收尾的记录）；未收尾的残键仍
  按 `created_at` 起算，避免残键永久占位。
