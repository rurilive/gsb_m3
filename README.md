# delayq

任务编排平台的延时队列，heapq 实现，时钟注入，纯标准库，无外部依赖。

## 模块说明

`delayq/queue.py` 提供延时队列 `DelayedQueue(clock=None)`：

- `add(task, delay, key=None)`：任务在 delay 秒后到期；key 相同的重复
  提交以最后一次为准，旧条目作废，不会被再次执行
- `pop_ready()`：只弹出已到期（due <= 当前时刻）的任务；同一时刻到期
  的任务按提交顺序出队；没有到期任务时返回 None
- `peek()`：距最近到期任务的等待秒数，消费端按它睡眠后再轮询；队列
  为空返回 None
- `len(q)`：当前生效（未到期且未被去重）的条目数

`delayq/clock.py` 提供时钟抽象：`SystemClock` 为进程默认时钟，
`FakeClock` 支持 `advance()` / `jump_to()` 手动推进，供测试注入。

## Known Issues

以下问题均已修复，根因记录如下，对应回归测试见 `tests/test_delayq.py`。

1. **未到点的任务被提前执行**
   根因：旧版 `pop_ready()` 无条件 `heappop` 堆顶，从不拿 `due` 和当前
   时钟比较，只要队列非空就会把最近的条目弹出——哪怕它还没到期。
   修复：`pop_ready()` 先看堆顶，`due > now` 时不弹出并返回 `None`，
   只在 `due <= now` 时出队；`peek()` 同步只考虑有效条目。

2. **同一时刻到期的任务执行顺序飘忽（不是先提交先跑）**
   根因：堆元素是 `(due, delay, entry)` 三元组，`due` 相等时用第二个
   字段 `delay` 比较；同刻任务的 `delay` 也相等时继续落到 `_Entry`
   对象地址比较（未定义稳定次序），顺序随内存布局变化，跨进程/隔天
   结果不同。
   修复：堆中直接存 `_Entry`，比较次序为 `(due, seq)`，`seq` 是提交
   时单调递增的全局序号，保证同刻任务严格按提交顺序（FIFO）出队。

3. **同一 key 重复提交，旧条目到期后仍被弹出执行**
   根因：旧版 `add()` 完全没有 key 维度的状态，重复提交只是往堆里再
   压一个条目，两个条目独立到期、各自弹出，等于执行了两次。
   修复：新增 `_active`（key -> 当前生效条目）映射。同 key 再次提交
   时把旧条目标记为 `cancelled` 并从生效计数中扣除；`pop_ready()` 与
   `peek()` 在堆顶惰性清理这些作废条目，旧条目永远不会返回给消费端。
   `len(q)` 也改为返回生效条目数，而不是堆长度。

4. **消费进程 CPU 打满空转，偶尔又一口睡过头错过整批任务**
   根因（空转）：`peek()` 直接返回堆顶的绝对到期时刻 `due`。时钟从 0
   或 FakeClock 从任意起点（demo 中是 100）开始时，返回值远大于实际
   等待秒数；而当堆顶恰好是被去重的作废条目时又可能给出 `0`，消费端
   `sleep(0)` 后立即轮询、弹不出任务，形成死循环式空转。
   根因（睡过头）：消费端按文档把 `peek()` 的返回值当“秒数”去 sleep，
   但拿到的是绝对时刻，于是一下睡到 `due` 那个时钟读数（可能是几百秒
   后），期间整批任务的预期执行时间全部错过。
   修复：`peek()` 返回相对等待秒数 `max(0, due - clock.monotonic())`，
   先惰性剔除堆顶的作废条目，队列只含作废条目时返回 `None`。语义与
   文档一致，消费端 `sleep(peek())` 既不会返回负数导致空转，也不会
   拿到绝对时刻睡过头。
