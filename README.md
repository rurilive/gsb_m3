# ringbuf

多生产者/多消费者定长环形缓冲，网关进程内嵌使用，纯标准库（threading.Lock）。

## 语义

- `put(item)`：写入一个元素，永不阻塞；缓冲满时覆盖最老元素，count 不会超过容量
- `get()`：取出最老元素；缓冲为空时抛 `ringbuf.Empty`；每条消息只会被一个消费者取到
- `count()`：当前元素个数，取值范围 [0, capacity]
- `snapshot()`：按逻辑顺序（写入顺序）导出当前内容的副本，不影响缓冲状态
- 所有操作线程安全，可在多线程读写场景下直接使用

## 运行

```bash
python3 demo.py
```

## Known Issues

以下问题已修复（防回归测试见 `tests/`）：

- **count 只涨不跌、超过容量**：`put` 在缓冲满时淘汰了最老元素却仍 `count += 1`，且 `get` 的 `count -= 1` 在锁外执行、并发下丢失更新。修复：满时淘汰与计数增减成对进行，`get` 的状态更新全部移入临界区。
- **两个消费者拿到同一条消息**：`get` 只在锁内读取元素，`_advance_head()` 与计数递减在锁外，第二个消费者可在游标推进前读到同一槽位。修复：读取、游标推进、计数递减整体置于同一把锁内。
- **缓冲未满却丢消息**：count 因上述缺陷超过容量后，`put` 的淘汰条件 `count == capacity` 永远为假，写游标回绕时直接覆盖未消费数据；此外 `_advance_head` 的回绕边界（`>= capacity`）与写游标（`> capacity`）不一致，读游标跳过最后一个槽位。修复：计数始终有界，读写游标回绕边界统一。
- **snapshot 顺序与写入顺序不符**：`snapshot` 直接截取底层数组前 `count` 个槽位，未从读游标按逻辑顺序遍历，还会混入空闲槽位。修复：从 `_head` 起按逻辑顺序收集 `count` 个元素。
