# raftlite

一个纯标准库的单机复制日志，无外部依赖。分布式存储、配置中心这类系统里都要把
一条条变更按次序记下来再复制到多个副本，raftlite 就是干这件事的那一层。

## 现状

- `raftlite/log.py`：`Log` 维护一条追加日志，索引从 1 开始。
  - `append(term, command)`：在末尾落一条 `Entry`，返回该条目
  - `entries()`：按索引次序返回全部条目的浅拷贝
  - `size()` / `last_index()` / `last_term()`：长度与末尾条目的索引与任期
  - `term_at(index)`：读某索引处条目的任期
  - `truncate_from(index)`：丢掉 index 及其之后的条目，返回被丢掉的条目
  - `commit_index()`：当前已提交到的索引
  - `reset()`：清空全部条目
- `raftlite/errors.py`：`RaftError` 基类与 `InvalidIndex` / `UnknownNode`
  两种具体错误。

现有实现只有一条单机日志：没有节点，也没有领导与跟随者，日志不会从一处复制
到另一处；条目记下来了也不知道有没有得到多数认可，更谈不上在多数确认之后才
提交并应用；任期只是一个数字，没有选举，谁也当不上领导；跟随者的日志若与领导
在某一处对不上，没有回退与覆盖的路子；状态机只是跟着追加次序应用，与提交与否
无关。

## 问题

单条日志谁也复制不了，同一个变更没法落到多个副本上；没有多数确认，一条刚记下
的条目是提交了还是悬着分不清，状态机可能把还没被多数认可的条目先应用了；没有
选举，给定时序与投票结果也选不出领导，任期该如何单调增长无从谈起；跟随者落后
或有冲突时不会回退覆盖，低任期的旧条目可能一直压着高任期的新条目；应用顺序与
提交脱节，同一批输入跑两遍未必得到同一个状态机。

## 目标

见任务描述。约束：

- 现有行为与 `tests/test_log.py` 基线一致（基线一个字不改）
- 纯标准库，Python 3.10+
- 非法索引 fail fast，空日志语义明确
- 同一时序输入必须跑出同一结果
